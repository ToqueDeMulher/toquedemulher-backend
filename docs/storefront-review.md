## Diagnóstico confirmado do site publicado

- O bundle público `index-BabxkrCv.js` aponta diretamente para `https://toquedemulher-backend.vercel.app`, prefixo `/api/v1`.
- As consultas públicas a `/health` do backend, `/api/v1/products` e `/api/v1/brasil/cep/70040010` pelo frontend retornaram HTTP 500. Não foi feita compra nem gravada cotação em produção.
- A CLI da Vercel, no projeto backend `prj_ailhxS4xGgkXfiYmnU1GOq0plp7j`, confirmou `psycopg2.OperationalError`: `EAUTHQUERY authentication query failed: connection to database not available`. A chamada `Database.create_db_and_tables()` no lifespan fazia a falha do banco impedir a inicialização de toda a API. Essa falha antes do middleware também explica a ausência de respostas HTTP tratadas para o navegador. O motivo específico da indisponibilidade do Postgres (estado do projeto, credencial, pooler etc.) não foi verificado.
- O rewrite `/api/:path*` já aponta para o backend e vem antes do fallback da SPA. Como o build publicado usa URL absoluta, as chamadas daquele bundle não usam esse rewrite. Há uma variável `CORS_ORIGINS` cadastrada; seu conteúdo não foi descriptografado.
- A listagem de nomes das variáveis de produção não contém `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `MELHOR_ENVIO_CLIENT_ID`, `MELHOR_ENVIO_CLIENT_SECRET`, `MELHOR_ENVIO_REDIRECT_URI` ou URLs `FRONTEND_*`. Valores secretos não foram lidos. Uma conexão OAuth salva no banco não pôde ser inspecionada.

Não gerar tabelas automaticamente em produção.

Conferir a aplicação, em banco local/staging isolado, das migrations existentes, especialmente `20260830180000_align_stripe_checkout_stock.sql`, `20260913173000_strengthen_integrity_and_organize_schema.sql`, `20260914163703_melhor_envio_shipping.sql` e `20260917184841_enable_shipping_rls.sql`. As migrations PostgreSQL/RLS não foram executadas nesta tarefa; os testes usam SQLite.
3. **Frete:** `MELHOR_ENVIO_ENVIRONMENT=sandbox`, client ID/secret, callback HTTPS da API em ambiente publicado, `MELHOR_ENVIO_USER_AGENT` com identificação/email reais e `MELHOR_ENVIO_SENDER` com CEP de origem e cadastro real completo para checkout/etiquetas. A faixa de frete gratuito vem de `MELHOR_ENVIO_FREE_SHIPPING_THRESHOLD`; `0` desativa. Confirmar a condição com a loja.
4. **Stripe:** usar exclusivamente chave `sk_test_...`, webhook de teste e `STRIPE_WEBHOOK_SECRET`. Configurar endpoint `/api/v1/payments/webhook` para `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired` e `charge.refunded`. Configurar `FRONTEND_SUCCESS_URL=https://<frontend-de-teste>/checkout/success` e `FRONTEND_FAILURE_URL=https://<frontend-de-teste>/checkout/failure`. O código adiciona `session_id`/`order_id`. Repetir eventos para conferir idempotência em staging. Não usar chaves live.
5. **Contato:** preencher `CONTACT_RECIPIENT_EMAIL` com caixa confirmada pela loja e configurar `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_STARTTLS`, `EMAIL_FROM`. `STORE_CONTACT_EMAIL` é opcional e só deve conter email autorizado para divulgação. 6. **Frontend:** em Vercel, definir `VITE_API_URL` vazio para usar o rewrite existente e `VITE_API_PREFIX=/api/v1`; alternativa é host HTTPS do backend com `CORS_ORIGINS` contendo a origem exata. Não usar localhost em builds públicos. Alterações em `VITE_*` exigem novo build. Retornos/OAuth precisam de `FRONTEND_URL` e, se usado, Google Client ID/origens corretos. ## Validação e limites

- Backend: `DATABASE_URL=sqlite:// SMTP_USER='' SMTP_PASSWORD='' .venv/bin/python -m pytest --rootdir=. tests/ -q`. Resultado: **98 testes passaram após integrar a branch de melhorias**, um aviso de depreciação do `crypt` em dependência existente. Cobertura inclui preço real, reserva/liberação, repetição de webhook, autorização, cotação vencida/alterada, frete, catálogo, SMTP aceito/recusado e indisponibilidade de banco.
- Frontend: Node 22.23.2, `npm run typecheck` e `npm run build`. Ambos passaram.
- Navegador: Playwright/Chromium, desktop 1440×1000 e celular 390×664 CSS px (perfil iPhone 13). **22 testes passaram**. Rotas da API interceptadas com fixtures exclusivas de testes; não houve contato com Stripe/Melhor Envio/SMTP reais. Capturas em `toquedemulher-frontend/artifacts/screenshots/`.
- Não houve alteração de variáveis externas, banco de produção, publicação, push ou compra real. As alterações locais anteriores de administração/produtos foram preservadas.
- **Ainda impede uma compra completa publicada:** acesso ao banco indisponível; integrações Stripe/Melhor Envio não verificadas e variáveis necessárias ausentes da listagem; dados do catálogo/remetente e migrations de produção não auditados; alterações desta revisão ainda não publicadas. Envio de atendimento exige destinatário/SMTP confirmados. A homologação externa deve ocorrer em teste após essas configurações.

Referências de integração: [Stripe: confirmação por webhook](https://docs.stripe.com/checkout/fulfillment), [Supabase: RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [documentação local do frete](shipping-integration.md).
